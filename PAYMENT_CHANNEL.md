# Experimental Payment Channel Protocol

This Node.js API implements two-party, co-signed state transitions using Ed25519 keys and unsigned integer credit units. It is not an escrow contract or a production payment system. The caller must independently validate the opening reference, funding, participant identities and eventual settlement. The SDK does not treat an arbitrary opening hash as proof of an onchain deposit.

`PaymentChannel` is a named export of `@ainblockchain/ain-js`. The HTTP helpers are available from `@ainblockchain/ain-js/lib/state-channel/http-peer`.

1. Both participants construct a channel from identical `ChannelOpening` values.
2. The sender calls `propose(from, amount, privateKey)`. This signs a proposal without changing its committed balance.
3. The recipient calls `accept(proposal, privateKey)`. Domain, sequence, previous-state hash, sender signature, amount and balance conservation are checked before the recipient co-signs.
4. The sender calls `commit(receipt)`, authenticating both signatures before changing its state. An exact signature over the exact canonical payload just generated by this instance is reused; received counterparty signatures are always verified. Independent journal replay verifies both signatures without that local cache.
5. If acknowledgement is lost, resend the identical proposal. The recipient returns its existing receipt for that state without applying the transfer again. A competing proposal for that sequence is rejected.

The canonical signature payload binds the opening hash, sequence, prior state hash, transfer direction, integer amount and resulting balances. Opening hashes include chain/channel identifiers, opening reference, public keys and initial balances. Snapshot objects are copies; mutating them does not change the channel.

`createPaymentPeer(channel, receiverKey, persist)` serves `/pay` and `/state`. The supplied asynchronous persistence callback must durably store each accepted receipt before resolving. The peer serializes requests, waits for persistence before acknowledging, and refuses further requests after a persistence error. Replay the durable receipts through `commit()` before accepting traffic after a restart. The example harness uses append plus fsync; a malformed or truncated journal is rejected rather than silently dropped.

`postPayment(endpoint, proposal)` transports one proposal over HTTP(S). Validate the returned receipt through `commit()`; HTTP success alone is not sufficient. Use TLS when confidentiality is required. A timeout is an observation failure, not permission to create a new transfer.

Verification performed in the reproduction workspace:
- SDK unit tests: conservation, wrong keys/signatures, malformed/insufficient amounts, cross-domain replay and conflicting sequences.
- Two Docker containers on an isolated bridge: 20 acknowledged transfers and 20 repeated deliveries; invalid signature, sequence gap and inflation rejected.
- Recipient killed after acknowledgements and restarted from the fsynced journal; balances, signatures and head match, and replaying the last proposal does not double-pay.

The baseline reproduction ran 100 channels (200 participant keys) for 60 seconds in separate sender/receiver Docker containers, each limited to 2 CPU and 4 GiB RAM. Every receipt was fsynced before acknowledgement. The measured window contained 40,071 transfers (667.85 TPS); 100 further acknowledgements arrived during drain and were excluded from TPS. All 40,171 committed transfers were independently replayed from the journals, with matching balances and heads. That baseline did not achieve 7,000 TPS.

Opening metadata and a final checkpoint were recorded on the local 10-node AIN chain, with finalized receipts, independent node readback and block inclusion checks. These are checkpoint records, not escrow deposits or payouts. Evidence run: `channel_network_load_20260911_r2`; opening transaction `0x3797325687029b6b747c65bab4d0b5893002e8f38819e538cad982f8796fff1d`, final transaction `0x968b9c07e70d2c431c2e90b5463460d5d5975b017653eefccc1943d462621f9d`. The full stability matrix and adversarial onchain dispute resolution remain incomplete.

## Parallel durable transport

`lib/state-channel/group-journal` exports `GroupCommitJournal`. It groups independent receipts into checksum-framed JSONL, handles partial writes, and resolves appends only after the batch fsync completes. Queue limits provide backpressure; write or sync errors fail closed. Creation uses an exclusive private file and syncs its parent directory. `replayGroupJournal` validates framing and reports an incomplete tail without modifying the file; callers must validate each receipt using a fresh `PaymentChannel` and decide recovery explicitly.

`lib/state-channel/batch-peer` exports `createBatchPaymentPeer` and `PaymentBatchClient`. Transport batches contain at most 128 independently signed channel updates; each update remains one actual transfer, not a sub-operation invented for counting. Same-channel requests and state reads share a queue. Duplicate delivery returns the existing receipt without another transfer or persistence acknowledgement. These helpers are an experimental loopback HTTP transport, not a public authenticated payment service.

`tools/state-channel/parallel-load.js` assigns independent channels to disjoint worker threads on both peers. A measured success requires receiver validation and fsync, receipt transport, sender validation and sender fsync. One monotonic measurement window is shared by all workers. Drain acknowledgements are reported separately and excluded from TPS. After the sender finishes, the runner kills only its own receiver, then independently replays both journals with fresh channel instances and compares every final state and transfer count.

`WARMUP_MS` defaults to zero. A nonzero warmup must be selected before the run and is recorded in both peer manifests. Warmup and drain transfers remain in both journals and the independent audit but are excluded from the predeclared measurement window. The summary reconciles total acknowledgements against warmup, measured and drain counts. Latency percentiles cover measured completions only. Never relabel a warm-start measurement as cold-start performance or select a favorable window after observing results.

Build with `tools/state-channel/refresh-sdk.Dockerfile` and explicitly selected SDK and native-chain base images. Run Node 22 focused tests with `node --test tools/state-channel/group-journal.test.js tools/state-channel/batch-peer.test.js` and `npx jest --runInBand __tests__/payment-channel.test.ts`. From a stable, unmodified source checkout:

```bash
RUN_ID=m2_unique_run AIN_CHANNEL_IMAGE=source-built-image \
CHANNELS=512 WORKERS=8 DURATION_MS=60000 CHANNEL_TRANSPORT=batch \
TRANSPORT_BATCH=16 JOURNAL_DELAY_MS=1 PEER_CPUS=4 PEER_CPU_SHARES=131072 \
bash tools/state-channel/run-parallel-load.sh /new/evidence /new/private
```

Do not edit the executing shell file. Evidence and private directories must be new, separate paths; do not delete prior runs to make the command succeed. The runner never replaces existing chain, model or trainer containers. Each peer has a 4-CPU quota, CPU set 0-7, 4 GiB memory with no extra swap, no GPU, and recorded CPU shares. Quotas on this shared 8-vCPU host are ceilings, not dedicated cores or an AWS performance equivalence.

For an explicitly provisioned, dedicated top-level systemd slice, `PEER_CGROUP_PARENT=yourbenchmark.slice` places only the new benchmark containers under that parent. Provision and record its aggregate CPU/memory limits separately; the runner records parent limits and does not change any existing slice. This matters because increasing a child's CPU weight cannot remove contention at its parent. The September 12 comparison uses a new parent capped at 6 CPUs and 8 GiB with no swap and CPU weight 1000, while keeping existing workloads running. This is a different CPU-allocation experiment, not evidence of a software-only speedup. Stop only the temporary keeper and empty benchmark slice after all its containers have exited.

These load openings are explicitly **unfunded capacity diagnostics**. They do not open an escrow, submit settlement transactions, prove remote-network performance or certify the complete State Channel KPI. Actual native escrow tests are separate; a checkpoint or an unrelated successful payout cannot turn these diagnostic transfers into funded payments. See `tools/state-channel/7000-tps-web-research-20260912.md` for the design rationale and official sources.

The September 12 repeated capacity measurements exceed 10,000 TPS mean with both peers durable and independently replayed journals. Final-source measurement: 10,521.08 TPS mean, 11,818 TPS one-second peak, 43 focused tests passing. Resource-allocation differences, all exploratory runs, public replay instructions and the incomplete funded-settlement gate are documented in `tools/state-channel/parallel-load-results-20260912.md`.
